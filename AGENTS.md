# LLM Wiki — Agent Constitution

You are working in a **two-layer LLM wiki**: a raw layer that mirrors a
reference library, and a wiki layer that synthesises what the raw layer
says. This file is the contract. Read it before touching anything.

Nothing here is specific to a field. The same rules work for a
literature base in medicine, law, materials science, machine learning or
anything else — the vocabulary comes from the sources, not from this
file.

## The two layers

| | `sources/` — RAW | `topics/` — WIKI |
|---|---|---|
| Written by | `scripts/zotero_sync.py` or `scripts/new_source.py` | **you** |
| Contains | one note per reference: frontmatter, abstract, embedded PDF | concept and theme pages synthesising the sources |
| Agent may edit | **never** | yes, this is your workspace |

`topics/` is the only folder you write to.

## Non-negotiable rules

1. **Never create, edit or delete anything under `sources/`**, including
   `sources/_index.base`. That folder is a projection of the user's
   reference manager and is regenerated by the sync adapter; anything
   you write there is silently overwritten or fights with it. If a
   source's frontmatter looks wrong, that is an adapter bug to **flag**,
   not something to hand-fix.

2. **Never rewrite a topic page wholesale.** Integrate new material into
   the relevant section and preserve everything else byte-for-byte.
   Topic pages may have been hand-edited since they were generated, and
   those edits are the most valuable text in the vault. Edit surgically:
   replace a specific passage, append to a specific list. Never
   regenerate a file from scratch to "update" it.

3. **New topics are proposed, not created unilaterally.** When sources
   fit no existing topic, present a candidate cluster — name, one-line
   rationale, the citekeys it would hold — and wait for explicit
   approval before creating the page. This applies on a first build too:
   see `.agents/skills/wiki-bootstrap/SKILL.md`.

4. **`python3 scripts/wiki_lint.py` is ground truth for "what needs
   attention."** Its ORPHANED list — sources cited by no topic page — is
   the definition of unprocessed material. Run it *before* starting any
   wiki-editing task and *again after*, to confirm nothing broke.

5. **Every claim traces to a `[[citekey]]`.** No exceptions, including
   sentences that feel like common knowledge in the field. If a source's
   abstract or notes do not actually support the claim you want to make,
   write "needs a closer read" and name the source instead of guessing.
   A gap you admit is worth more than a claim you invent.

6. **Never add anything to the reference manager, and never write into
   `sources/`.** Literature selection is a human decision. Papers found
   through external search go in `candidate-sources.md` for review. Your
   job is finding and de-duplicating candidates, not enrolling them.

7. **Report disagreement rather than smoothing it.** When two sources
   conflict, say so and attribute each side. When a source's abstract
   contradicts its own results table, that is a finding — record it.

## Structure of the wiki layer

Three tiers, distinguished by the `tags` field:

- **`domain`** — a top-level area. An overview plus links to sub-topics;
  carries no `parent`. Aim for 3–8 across the whole vault.
- **`hub`** — optional middle tier, created only when a topic grows big
  enough to split. Has a `parent`.
- **`topic`** — a leaf. **Synthesis lives here**, and only leaves carry a
  `## Sources` list.

Every non-`domain` page needs a `parent` that resolves to a real page.
`scripts/wiki_lint.py` enforces this.

Which tier a page belongs to follows from two structural facts, so it is
never a judgement call:

| tags | has `parent` | has its own `## Sub-topics` |
|---|---|---|
| `[domain]` | no | yes |
| `[hub]` | yes | yes |
| `[topic]` | yes | no |

### The domain list is fixed once agreed

The domains are settled with the user at bootstrap and then treated as
established. **Do not invent a new domain, and do not retire one.** New
material becomes a new *topic* under an existing domain. If something
genuinely fits nowhere, raise it as an observation and let the user
decide — changing the list is a separate, deliberate conversation.

### Staging files

`topics/uncategorized.md` is **not** part of the hierarchy: it carries no
`parent` and no `status`, and the lint exempts it. **A citation from a
staging file does not count as processing a source** — parking something
records why it is waiting, it does not synthesise it — so those sources
stay in the ORPHANED list. That is deliberate: it makes the lint alone
the complete queue of unprocessed material, with nothing to combine by
hand. It holds sources that
have not clustered yet, plus clusters awaiting approval, so a proposal
survives between sessions. Re-read it on every update — a source that did
not cluster last time may cluster with new arrivals.

### Topic page frontmatter

```yaml
---
tags: [topic]          # exactly one of: domain | hub | topic
parent: "domain-slug"  # required unless tags is [domain]
status: stub           # stub | drafted | linked
last_updated: 2026-10-07
---
```

`status` tells a future agent what is left to do, and drives the
"Needs filling" / "Needs linking" views in `topics/_index.base`:

| status | means |
|---|---|
| `stub` | created from a quick skim — overview and source list only |
| `drafted` | filled in from a **deep read** of its sources |
| `linked` | cross-linked to siblings, multi-homing resolved |

Always bump `last_updated` when you change a page.

### Naming topics

**Keep slugs concise: 2–4 words, 5 at the absolute maximum.** A slug is
read inside a wikilink mid-sentence and inside a graph view, where long
names are unusable. `thermal-management` over
`thermal-management-and-cooling-technologies-overview`. Prefer the term
of art a practitioner would actually say out loud. The lint warns above
five words.

Slugs are lowercase, hyphen-separated, and stable — renaming one breaks
every `[[link]]` to it, so choose carefully rather than renaming later.

### A source can belong to several topics

This is normal and expected, not a problem to resolve. A paper spanning
two themes is cited by both pages, with each page citing it **for the
part that is relevant there**. Do not copy the same paragraph into both.
`wiki_lint.py` reports the multi-homed count as information, never as an
error.

## Reading sources: skim vs deep read

Deliberately two different operations, and using the wrong one is the
most common way to waste a session:

- **Skim** — frontmatter plus the `## Abstract` section. Cheap. Enough
  to decide *where a source belongs*. Never enough to state a finding.
- **Deep read** — the embedded PDF, or the full text. Expensive. The
  only basis for a specific claim: a number, a method, a limitation.

Use `has_pdf` in the source frontmatter to know whether a deep read is
even possible. When it is not, say so on the page rather than inferring
from the abstract.

## Checkpointing: write each source's findings before reading the next

**A deep read that is not written down is lost.** Your context can end at
any point — token budget, an interrupted session, a crash — and anything
held only in context goes with it. So the unit of work is **one source**,
not one page:

> Read one source → write its findings onto the page → mark it in
> `## Sources` → only then open the next source.

Never read five PDFs and write them up together. Reading twelve sources
and writing nothing risks losing twelve reads; reading one and writing it
loses at most one.

### Mark each source as you go

In the page's `## Sources` list, annotate each entry the moment you have
dealt with it:

```markdown
## Sources
- [[citekeyA]] — deep read 2026-10-07
- [[citekeyB]] — abstract only (no PDF)
- [[citekeyC]] — abstract only (PDF unreadable: scanned, no text layer)
- [[citekeyD]]
```

An unannotated entry means **not yet examined**. That makes resuming
mechanical rather than guesswork:

```bash
python3 scripts/wiki_digest.py --topic <slug> --chars 0
```

prints a `RESUME HERE` list of exactly the sources still unexamined. Start
any deep-read session with that call, and never re-read a source already
marked `deep read`.

These markers also serve the reader: "abstract only" is the visible
warning that a claim rests on an abstract, which rule 5 requires you to be
honest about.

### A page is `drafted` only when every source is marked

While sources remain unannotated the page stays `status: stub`, even if it
already has substantial prose. Promote it to `drafted` only once the
`## Sources` list is fully annotated. The two fields answer different
questions: `status` tracks the page, the markers track progress within it.

**One exception, for pages written before this convention existed.** A page
already marked `drafted` or `linked` whose sources carry *no* markers at
all predates the convention — its sources were read, the page's own prose
is the evidence, and the markers simply were not a thing yet. **Do not
demote such a page to `stub`, and do not re-read its sources wholesale.**
`wiki_digest.py --topic <slug>` detects this case and says so instead of
printing a resume list. Add markers opportunistically when you next touch
one of those sources for another reason; a bulk backfill would be guessing
about which were read deeply versus from the abstract, and guessing is
exactly what rule 5 forbids.

### Incremental writing vs organising by claim

Writing source-by-source pulls toward a paper-by-paper page, which
`## What the literature says` must not be. Resolve it in two passes:

1. **As you read**, put each source's findings under the themed lead-in
   they belong to, creating a new theme when none fits. Order will be
   imperfect; that is fine — it is on disk and safe.
2. **Once every source is marked**, do one consolidation pass: merge
   near-duplicate themes, resolve redundant restatement, and put the
   themes in a sensible order. This is cheap, because the material is
   already on the page and needs no re-reading.

Never defer pass 1 to keep pass 2 tidy. A rough written page beats a
perfect unwritten one.

## Before finishing any task that touched `topics/`

1. Run `python3 scripts/wiki_lint.py` and report everything it flags.
2. Summarise: which pages you **edited**, which you **created** and from
   which citekeys, how many sources are still orphaned, and anything you
   deliberately left undone.
3. Never claim the lint is clean without having run it.

## Where things live

```
sources/            RAW layer — off-limits (incl. _index.base)
topics/             WIKI layer — your workspace
  _index.base       Obsidian Bases views; yours to use, not to rewrite
  uncategorized.md  staging: unclustered sources + pending proposals
templates/          the frontmatter contract, with notes on each tier
candidate-sources.md  externally-found papers awaiting human review
scripts/
  wiki_config.py    paths + the frontmatter parser; no hardcoded paths
  wiki_lint.py      read-only integrity check — ground truth
  zotero_sync.py    OPTIONAL Zotero adapter; you never run or edit this
  new_source.py     add a source by hand, without a reference manager
.agents/skills/     the workflows above
```

`scripts/` is not yours to edit as part of a wiki task. If a script is
wrong, say so and stop.
